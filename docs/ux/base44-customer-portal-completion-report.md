# Base44-exact rebuild: Customer Portal Completion

Branch: `rebuild/base44-customer-portal-completion` (worktree `C:\dev\Premier-CRM-customer-portal-completion`)
Base commit: `a136ab9` (PR #135 merged — site-visit undo-start fix)
This is a new slice of the Base44-exact rebuild program, closing out the customer portal after every internal-facing (staff) surface had already been ported.

**Scope-honesty note, up front.** This slice deviates from a literal component-for-component port of the 11 Base44 portal files. The Base44 reference components (`CustomerHome.tsx`, `MessagesView.tsx`, `QuotesView.tsx`, `InvoicesView.tsx`, `PropertiesView.tsx`, `AppointmentsView.tsx`, `AccountView.tsx`, etc.) are fixture-driven presentation shells built against a fictional `Quote`/`Invoice`/`Appointment`/`ChangeOrder` data model (`src/contracts/customerPortal.ts`) that does not line up 1:1 with Premier's real schema — most visibly, Base44's model assumes a working payment flow and a staff-reply message thread, neither of which exist in this codebase (confirmed, not assumed — see Audit findings). Rather than importing the Base44 JSX verbatim and then fighting its prop contract against real data it was never designed to carry, this slice **originates** Forge-native presentation for each nav section, in the same shadcn Card/Button idiom every other page in this program already uses, built directly against the real, already-existing query layer. This is the same honest characterization the Route Planning slice used for its own originated (not ported) presentation layer. Base44's markup was read and used as the structural/informational reference (what fields to show, what actions to expose, what NOT to expose) for every section; it was not copy-pasted.

The nav *structure* (Home, Messages, Requests, Quotes, Change orders, Invoices, Properties, Appointments, Account; mobile = 4 primary + More sheet) **is** taken directly from the Base44 boundary doc and implemented as specified.

## What was built, by section

**Home** — unchanged in substance from the existing real dashboard (`apps/web/app/portal/dashboard/page.tsx`): active/completed requests, properties, per-job cards (scheduling-slot booking, deposit state, working-invoice running total, change-order threads with respond/comment forms, job timeline, customer-safe site-visit summaries). Refactored only to: extract the auth+account-resolution boilerplate into `_lib/portal-session.ts` (`resolveActivePortalAccount()`), wrap the page in the new `PortalShell` nav chrome, and replace the literal `"Coming soon"` account-balance summary tile with a real link to the new Quotes/Invoices page. The `SummaryCard` component gained an optional `href` (renders as a `<Link>` when present, unchanged otherwise).

**Messages** (`apps/web/app/portal/messages/page.tsx`, new) — real data: the customer's own past `portal_contact_requested` `activity_log` entries, read via `_lib/portal-messages.ts`'s `listPortalMessages()`. `activity_log` has **no customer-facing SELECT RLS at all** (org-member-only, confirmed by reading `20260731010000_activity_log.sql`) — every read goes through the service client, narrowly scoped by this file itself via `.eq('org_id', ...).eq('event_type', 'portal_contact_requested').contains('related_ids', { customer_id })`, never a bare org-wide read. The existing `PortalContactSheet` ("Contact Premier") form is surfaced here as the primary way to start a new message. The page states plainly that there is no in-app reply thread — replies happen by the method the customer chose (phone/email/text) — rather than fabricating a staff-reply UI, per the task's explicit instruction not to fake a thread model that doesn't exist. Per-change-order comments (already real, `AddChangeOrderCommentForm`) remain on the job card on Home; Messages links there rather than duplicating that thread.

**Requests** (`apps/web/app/portal/requests/page.tsx`, new) — full list of the customer's own service requests (all statuses, not just active/completed split), reusing the same status-label/description helpers Home already used. **New-request creation was not wired** — see the Requests stop condition below; the page states this honestly and points to Contact Premier instead of a broken/fake form.

**Quotes** (`apps/web/app/portal/quotes/page.tsx`, new) — the first of the two real, closeable gaps. Built exactly per the audit's prescribed pattern: the customer's own `jobs` and `service_requests.estimate_id` are confirmed as owned via the RLS-scoped `portalClient` (`.eq('customer_id', account.customerId)`) first; only then does `_lib/portal-quotes-invoices.ts`'s `listPortalQuotes()` call the service client's already-existing `listQuotesForJob`/`listQuotesForEstimate` (`packages/db/queries/quotes.ts`, `packages/db/queries/estimates.ts`) scoped to those specific already-owned ids. This is **not a new authorization model** — it is the identical shape the dashboard already trusted for `getDepositState`/`getWorkingInvoiceSummaryForCustomer`/`listChangeOrdersForJob` before this slice. Each quote links out to the real, already-existing `/q/[token]` approve/decline page via its real `share_token` (fetched in a small follow-up batch for estimate-stage quotes, since `listQuotesForEstimate`'s narrower `select()` doesn't project it) — no second, parallel approval flow was built. `PortalQuoteRow` is a deliberately narrow, customer-safe projection (id/number/title/status/total/createdAt/shareToken/sourceLabel only), not the full internal `quotes` row — asserted by a unit test that no internal field (notes, terms, created_by, pricing-review state) can appear in its type.

**Change orders** — already real (respond/comment forms, revision history, price impact) and unchanged; the nav's "Change orders" entry deep-links to the Home job-cards section (`/portal/dashboard#jobs`) rather than building a second, thinner cross-job listing page, since change orders have no standalone list model independent of a job in the real schema.

**Invoices** (`apps/web/app/portal/invoices/page.tsx`, new) — the second real gap, built the same ownership-then-detail-fetch way via `listPortalInvoices()` → `listInvoicesForJob`. Real customer-safe fields shown inline: status, total, amount paid, amount due, issued/due dates. Each invoice links to the real, already-existing `/i/[token]` view via its `share_token`. **`kind === 'working'` invoices are explicitly excluded** — `isPortalVisibleInvoiceKind()`, unit-tested — matching the real `customer_select_own_invoices` RLS policy's own exclusion (working invoices carry internal notes) even though this read path goes through the service client and RLS itself doesn't apply; the boundary is a customer-safety rule, not just a grant, so it's enforced here in application code too. **No "Pay now" button was built** — no payment processor exists anywhere in this codebase (confirmed by grep, matching the Finance slice's own prior audit) — the page states "Contact Premier... to arrange payment," consistent with `/i/[token]`'s existing language, and is asserted by an E2E test that no such button exists.

**Properties** (`apps/web/app/portal/properties/page.tsx`, new) — dedicated page for the properties list already shown inline on Home, with a real "Open in Maps" link per property using the existing shared `buildOpenInMapsUrl()` (`apps/web/lib/maps/external-maps-url.ts`, from the Route Planning slice). The address itself is shown (matching the Route Planning slice's own precedent of showing full addresses, not gating them) — only the `MapsDestination` type's structural exclusion of gate codes/access notes is reused, consistent with that slice's established discipline.

**Appointments** — no standalone appointment/booking model exists independent of a job's scheduling-slot flow (already real on Home: `listOpenSchedulingSlots` + `BookSchedulingSlotForm`). The nav's "Appointments" entry deep-links to `/portal/dashboard#jobs` for the same reason as Change orders, rather than building a thinner duplicate list.

**Account** (`apps/web/app/portal/account/page.tsx`, new) — real, minimal: display name/phone from `customers`, portal sign-in email from `customer_accounts`, and sign out. No profile-editing form was built (not in the confirmed-gap list; editing customer records from the portal would be a new write surface requiring its own review) — the page states this and points to contacting Premier instead.

**Nav shell** — `_components/portal-nav.tsx` (desktop sidebar `#171717`/`#ea580c`, mobile bottom bar with 4 primary links + a native `<details>` "More" sheet for the rest — no client JS needed for a static disclosure), `_components/portal-shell.tsx` (auth/unlinked-account gate + chrome wrapper, `requirePortalUser()`), `_lib/portal-nav-links.ts` (the 9-item nav list matching the boundary doc's structure exactly), `_lib/portal-session.ts` (`resolveActivePortalAccount()`, extracted once from the dashboard's own inline logic so every new page uses the identical check).

## Audit findings relied on (and one correction to the task brief)

Everything in the task brief's own audit was verified true except one item, which had changed underneath it:

**Request creation is a genuine stop condition, not a "wire it up" case.** The task brief cited a live, unused RLS INSERT policy (`customer_insert_own_portal_service_requests`) as ready to wire up directly. Re-grepping the migrations directory found that policy — along with the entire `INSERT`/`UPDATE`/`DELETE` grant to `authenticated` on `service_requests` — was **deliberately revoked** by a later migration, `20260803080000_harden_service_requests_estimates_site_visits.sql`, dated after whatever snapshot the task brief's audit was run against. That migration's own comments state explicitly: *"an unused authorization path is not preserved merely because it already exists; a portal-submission feature, if built later, should be designed and reviewed as a deliberate addition, not inherited from a policy nobody currently exercises."* Building request creation this pass would mean either reopening that closed door with a new migration (a scoped RLS policy or, better, a `SECURITY DEFINER` RPC matching the pattern the hardening migration itself prefers) or a new server action using the service-role client with equivalent server-side validation — both genuine additive changes requiring review, exactly the kind of case this slice's own instructions say to stop on rather than route around. **No migration was written or applied.** The Requests page states this honestly in the UI and points customers to Contact Premier instead.

Every other audited item held: quotes/invoices have zero authenticated linkage and were the two real gaps closed this pass; `activity_log` has no customer RLS (used service-client + narrow app-level scoping); no payment processor exists anywhere; site-photo customer-safe visibility is a genuine schema gap and was **not built** (no `vault_items` column touched, per the task's explicit instruction).

## Security / RLS verification performed

- Every new page resolves the authenticated customer via `resolveActivePortalAccount()` (portal-scoped/RLS client), confirms `customer_accounts.status === 'active'`, and only then queries `jobs`/`service_requests` with an explicit `.eq('customer_id', account.customerId)` before any service-role call — the same ownership-then-detail-fetch order the pre-existing dashboard already used.
- `listPortalQuotes`/`listPortalInvoices` (`_lib/portal-quotes-invoices.ts`) only ever call the service client with job/estimate ids drawn from that already-confirmed-owned set — never a client-supplied id passed through unchecked.
- `listPortalMessages` (`_lib/portal-messages.ts`) is the one new place a broad-table (`activity_log`) service-client read happens; it is scoped in the query itself (`org_id` + `event_type` + `related_ids @> {customer_id}`), never returning another customer's or org's rows.
- `isPortalVisibleInvoiceKind()` enforces the `customer_select_own_invoices` RLS policy's `kind != 'working'` exclusion in application code too, since that boundary is a customer-safety rule (working invoices carry internal notes), not just a grant — unit-tested.
- Re-confirmed via the migration hardening pass (`20260803080000...sql`) that `service_requests`/`estimates`/`site_visits` direct-write policies were already closed for `authenticated` before this slice touched anything — this slice does not reopen any of them.
- No new migration was written or applied anywhere in this slice.
- `buildOpenInMapsUrl()` calls on the new Properties page pass only address fields (`MapsDestination`'s type structurally excludes gate codes/access notes), matching the Route Planning slice's own established discipline.

**E2E — executed live against `premier-crm-e2e` (`slbnizoskumwhleeiccv`), confirmed via `/api/e2e-health` before any test ran.** During independent verification, all 5 authenticated tests initially failed on the *first* real assertion (`toHaveURL(/\/portal\/dashboard/)`) — not a product defect, but a real bug in the spec's own login helper:

1. **`loginAsPortalCustomer()`'s use of `supabase.auth.admin.generateLink({ type: 'magiclink' })` does not work in this project's configuration** — the browser consistently landed on `https://www.ppmnky.com/customer-portal#access_token=...` (the real marketing site, with tokens in the URL fragment) instead of the requested `redirectTo`. Confirmed this is specific to the `magiclink` type, not an environment-wide issue: `portal-auth-bot.spec.ts`'s existing `signup`/`recovery`-type links both correctly honor `redirectTo` (re-ran that spec live to confirm, 2/2 passing). `magiclink` also isn't an auth method this app actually offers customers (confirmed in the original audit — real sign-in is `signInWithPassword` via the marketing-site handoff). **Fixed** by rewriting the helper to drive the actual production login path instead: a real `POST /portal/handoff/sign-in` (the same route the marketing site posts to), using Playwright's request context (which shares the browser's cookie jar with `page`) and the `http://localhost:5173` origin the marketing site's local dev server would send under `NODE_ENV=development` (`customer-portal-handoff.ts`'s `DEV_ALLOWED_MARKETING_ORIGINS`). This exercises the real `signInWithPassword()` + `ensureCustomerAccount()` route handler end to end — not a synthetic cookie injection, and arguably a better test than the original since it now also re-verifies the real handoff route on every run.
2. Two invoice-view assertions checked for the invoice's own `title` field, which the real `/portal/invoices` page deliberately doesn't render (it shows `invoiceNumber` + `jobTitle` instead — a real, sensible product choice, not a bug). Fixed to assert against what's actually shown.
3. A strict-mode collision: the desktop nav's exact "Quotes" link collided with the dashboard's inline "Quotes and invoices" summary card link, and the mobile bottom nav's `<nav aria-label="Portal navigation">` collided with the desktop sidebar's identical landmark label (both render in the DOM simultaneously, CSS-hidden per breakpoint — same recurring dual-layout pattern as every prior slice). Fixed by scoping to the first (desktop) nav landmark with `exact: true`.

**One real product defect found and fixed**: the dashboard's "Signed in as {email}" text and the new Account page's "Portal sign-in email" text both had no word-break constraint against long fixture-data email addresses, causing an 8px horizontal overflow at mobile (390×844) — the exact same recurring bug class as every prior slice's tables/cards. Fixed with `break-words` on both.

After fixes, all 6 tests in `portal-completion-base44-shell-bot.spec.ts` pass live, including genuine two-customer isolation (customer B's session never sees customer A's request/quote/invoice text and vice versa, verified against real, separately-created fixture data) and a real assertion that no "Pay now" button exists anywhere on the invoices view. Re-ran the full suite alongside `portal-auth-bot.spec.ts`, `jobs-base44-shell-bot.spec.ts`, and `properties-base44-shell-bot.spec.ts` (since `tests/e2e/utils/auth.ts`, a shared file, was modified) — 31/31 passing, confirming the login-helper rewrite didn't affect any other spec's use of that file. Visual evidence captured live (dashboard, quotes, invoices, messages, requests, properties, account, desktop + mobile) via a throwaway fixture-and-teardown script — confirmed correct: real 9-item nav, real data throughout, the fixed "Coming soon" placeholder now a real "Quotes and invoices → View" link, the email wrapping correctly instead of overflowing, and the invoices view's honest "Contact Premier to arrange payment — there is no online payment option in the portal yet" message. Zero test-data residue confirmed via SQL after each run (this fixture reuses the shared demonstration org rather than creating a fresh one — cross-*customer* isolation within that org is what's being verified, not org isolation, so this doesn't weaken the test; see the corrected spec docstring).

## Known limitations / follow-ups

1. Request creation was not wired — see the stop-condition gap table entry and proposed `create_portal_service_request()` RPC model above.
2. Site-photo customer-safe visibility was not built (task instruction) — remains a genuine schema-decision gap.
3. Messages has no staff-reply thread — stated honestly in the UI rather than fabricated; a real thread model (`message_thread`/`request_messages` table) would be a future schema addition.
4. Account profile editing (name/phone/email) is read-only this pass.
5. Base44's 11 portal presentation components were used as structural/informational reference, not ported verbatim — see the scope-honesty note. Visual fidelity to Base44's literal markup cannot be claimed; fidelity to its nav structure and customer-safe boundary rules can.
6. The "Portal account not linked yet" unlinked-account state was not separately E2E-covered this pass (unchanged code path from the pre-existing dashboard); confirmed unchanged during independent verification but not newly tested.
