**Product decision recorded 2026-08-11**: Forge V1 does **not** require customers to pay online through the product. Manual payment handling (staff records payment method/amount/date/reference by hand; portal shows an honest "Contact Premier to arrange payment" link-out, never a fake "Pay now" button) is the accepted V1 posture. The online payment-processor gap (§3) is reclassified from P0 to P2 — a valuable post-V1 capability, not a launch blocker. No vendor has been selected; no payment code has been written as part of this decision.

## 11. Product decisions still needed (recorded 2026-08-13)

**F6 and F2 (Production readiness §9) — RESOLVED 2026-08-13.** `customer_archetype_defaults` now has RLS enabled (read-only for `authenticated`, write restricted to `service_role`; `20260813010000_customer_archetype_defaults_rls.sql`). `createEstimateFromRequestAction` now delegates to `record_request_triage` instead of duplicating its transition logic, so it stays in sync with `triage_decision`/`triage_reason`/`triaged_by`/`triaged_at` and — as a direct consequence of using the RPC's own gate — is now restricted to `canTriageRequests` roles (closing an until-now-undocumented viewer write path this legacy action had no capability check for at all). See PR "fix/v1-security-triage-integrity" for the full audit and live proof.

**Portal urgency/priority self-declaration — RESOLVED 2026-08-13, Option B.** Decision: customers may report `routine`/`soon`/`urgent` via a separate `customer_reported_urgency` column on `service_requests` (`20260813020000_portal_customer_reported_urgency.sql`), never mapped into `priority`. No "convert urgency to priority" action was built — there is no general priority-editing workflow at all today, and one was not invented just to close this gap; staff sees the customer's signal on the request list, detail header, and TriagePanel as labeled context ("Customer reported: Urgent" vs. "Internal priority: Normal") and makes the actual triage decision themselves. `service_requests.priority` remains exactly as staff-authoritative as before — live-verified (`tests/e2e/portal-request-creation-bot.spec.ts` tests 8–12) that selecting any urgency value, including "urgent", leaves `priority` at its untouched default, and that direct authenticated `UPDATE ... priority` still fails.

**CP-4 — RESOLVED 2026-08-13.** Decision: a single `canManageCustomers` capability (`owner`/`admin`/`employee`; **subcontractor and viewer excluded**, deliberately narrower than the repo's general operational-capability pattern — customers/properties are the CRM's authoritative master identity/contact/location records, not routine field work, and the decision was to start narrow and widen later only if a real operational need appears) now gates the only two operations that exist (`createCustomerAction`, `createPropertyForCustomerAction`; no archive/delete capability was invented since no archive/delete action exists yet). Live-verified end to end through the real UI, not mocked (`tests/e2e/cp4-customer-property-authorization-bot.spec.ts`, 11/11): owner/admin/employee succeed, subcontractor/viewer are rejected server-side with no row created.
